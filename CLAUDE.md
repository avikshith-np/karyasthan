# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Karyasthan ("caretaker" in Malayalam) is a WhatsApp group chat AI agent that acts as a real person in group conversations. It uses Baileys (WhatsApp Web API) for messaging and an LLM for response generation. Core philosophy: be a participant, not a servant — respond selectively, be opinionated, remember people, build relationships.

The persona is **fully configurable** — each install generates its own. `npm run setup` (guide: `docs/install.md`) offers a starting character from `src/personality/templates/`, then a few questions, and writes the bot's identity.

### Persona files

The persona lives in two gitignored files under `src/personality/`, both generated by the setup wizard:

- **`persona.json`** — structured fields the *code* reads: `name`, `displayName`, `aliases[]` (names the bot answers to), `voiceDescriptor`, `region`, `language`, `vibe`. Loaded via `getPersona()` in `src/utils/config.js`.
- **`identity.md`** — free-form prose injected verbatim into the LLM system prompt.

Committed references (used as fallbacks if the real files are missing, and as the template the wizard renders from): `persona.example.json`, `identity.example.md`, `identity.template.md`. Never hardcode a persona name or language in code — read it from `getPersona()`.

## Architecture

The message processing pipeline flows through these stages:

1. **Memory extraction** (`src/memory/learningPipeline.js`) — async, non-blocking. Fast heuristics on every message; LLM batch analysis every 100 messages per group.
2. **Decision engine** (`src/brain/decisionEngine.js`) — multiplicative 8-factor probability model (mention, question, command/request, humor, momentum, recency, BS detection, two-person conversation), plus an imitation-cadence multiplier while imitating. Direct mentions bypass probabilistic scoring at 95% confidence.
3. **Audio transcription** (`src/brain/transcribe.js`) — downloads voice messages via Baileys and transcribes using OpenRouter or native Gemini API. Transliterates non-English audio to English script.
4. **LLM generation** (`src/brain/contextBuilder.js` + `src/brain/llm.js`) — builds system prompt from identity doc + group context + people profiles + memories, then calls LLM. Multi-provider: OpenRouter (primary), Anthropic, OpenAI, Gemini, Zhipu GLM, xAI, Ollama (local fallback). When the **web-search** skill is enabled, `generateResponse` runs a bounded **marker + re-prompt loop**: the LLM may emit `[SEARCH: query]` / `[BROWSE: url]` as its whole message, the tool runs (`src/brain/webSearch.js` SearXNG / `src/brain/webBrowse.js` Playwright), the sanitized results are appended to the user message, and the LLM is re-prompted to answer in voice. Every model call goes through a **role** (`callRole`/`callLlm` in `llm.js`, see "Model roles, usage ledger & budgets"). See "Web search & browsing" below.
5. **Post-processing** (`src/brain/postProcess.js`) — strips AI artifacts, markdown, splits long messages.
6. **Humanization** (`src/behavior/timing.js`) — context-aware response delays, typing indicator simulation (refreshed every 7s), delayed read receipts. With the **life** skill on, an availability gate runs before all of this and his phone owns receipts/presence — see "Life simulation".

Orchestrated by `src/index.js` which is the main event loop.

- **`src/whatsapp/`** — Baileys socket connection, event handlers (message upsert, group updates), send actions (text, reactions, typing, read receipts, presence)
- **`src/memory/`** — SQLite (better-sqlite3) storage. Schema in `schema.sql`. Tables: messages (with FTS), people, groups, nicknames, relationships, slang, memories
- **`src/behavior/`** — Rate limiter, timing, warmup schedule for new deployments
- **`src/personality/identity.md`** — Full character definition. `systemPrompt.js` dynamically assembles the prompt from identity + learned context

Routes under `src/dashboard/routes/`; static SPA in `src/dashboard/public/` (vanilla ES modules, no build step — see "Dashboard" below).

## Important Patterns

- **JID format**: WhatsApp uses `sender@s.whatsapp.net` (individuals) and `groupid@g.us` (groups) — JID utilities in `src/utils/jidUtils.js`
- **Memory privacy (spec 006)**: every memory-like row (memories, person facets, nicknames, relationships, slang) carries `origin_kind` (`self|group|dm|call|ig|owner`) + `origin_jid` + `learned_at` (= earliest evidence message). Every prompt surface builds an `Audience` (`resolveAudience` in `src/memory/recall.js`) and reads only through `recall` / `recallFacets` / `recallNicknames` / `recallRelationships` / `recallSlang` / `recallExemplars`. Rule: same chat → usable; DM/call origin → that DM only (calls belong to the caller's DM); group/IG origin X → chat Y only if Y's members are non-empty, contain no outsiders, both memberships are fresh, and every Y member joined X at or before `learned_at`; derived items AND over all their origins; underived self content → anywhere. Fails closed (recall error → own chat + self only; unknown identity → outsider). Direct SQL reads of these tables for prompts are banned outside `src/memory` and dashboard routes (import guard in `test:privacy`). The dashboard (operator view) still sees everything; owner notes default to visibility `subject_dm`.
- **Identity + membership**: `src/memory/identity.js` canonicalises LID ↔ PN (`resolvePerson`, `recordIdentity` from Baileys alt ids and `lid-mapping.update`; a recycled number is a reassignment, not a merge; merges where either side has DM data go to `identity_merge_queue` for owner approval; a pair the owner rejected is not queued again unless evidence of another class arrives — the reason is `<conflict|dm_data>:<source>` and a rejection is keyed on the pair + class only, since the source is just the delivery channel, and the person page lists rejected pairs). `src/memory/membership.js` does a full `groupFetchAllParticipating` sync on each connect + every 3h; freshness is 7h (IG 26h); real join/leave times are logged in `group_membership_log`. Retention purge and orphaned-voice removal are gated on `membershipGate()`.
- **Learning**: batch analysis (`learningPipeline.js`) uses P-labels + line ids so every fact cites human evidence messages (bot lines never count); persists facts/facets/relationships/lore/slang with provenance, fingerprint dedupe and same-origin supersession; per-chat `learning_state.last_batch_rowid` (DMs included); a batch reads the oldest pending lines (≤ 150) and, when more are pending, advances only to its last line and leaves the counter at the threshold so the next message runs a follow-up batch. An identity merge keeps an unknown `learned_at` / `min_learned_at` unknown (NULL never crosses chats). `no_learn`, expired (disappearing) and revoked messages are never evidence and never reach prompts (`getRecentMessagesForPrompt`).
- **Forget / revoke / purge**: a whole-message "forget that" in a DM (detected in `events.js` before debouncing) fences the sender's last few messages (`no_learn`), deletes items they evidence and writes content-key tombstones in `learning_exclusions` so the claim isn't relearned. Revokes/edits are applied only within their own chat. Deleting a slang row recomputes `is_global` for its term (a term left in one chat stops being global); a restated claim whose temporary copy already expired takes the new expiry. The owner's dashboard delete of one memory is `deleteMemory` (`relationshipStore.js`, `DELETE /api/memories/:id`): same machinery as forget — a learned memory is tombstoned (an owner note is not), and the `onItemsDeleted` listeners run with cause `'owner'` and `msgTs` = the memory's `created_at`. `purgePerson` removes a person's scoped data (audited; clears the identity cache after the commit), and revokes their cloned voice in the same transaction (`revokeVoicesForPurge`, marked "Google delete pending"); the caller then runs `voiceClone.retryPendingVoiceDeletes()` and the 6-hourly maintenance retries any delete Google didn't confirm (a purged row goes once it does).
- **Relays**: "tell the group I'm late" in a DM → code prefilter → Jev intent check → code decision (named group, fresh membership, requester is a member, not forwarded, no credit-name collision) → the bot asks and the reply must carry `[RELAY_OK]` → `relay.dispatch` posts via `withChatLock` with the normal gate/mute/warmup/caps/DRY_RUN path. Pending relays expire after 10 min. Relay text is generated from the relay content only, never from DM context.
- **Migrations**: `PRAGMA user_version` ladder (`src/memory/migrations/`, append-only; `schema.sql` is the frozen v0 baseline). Before stepping, `VACUUM INTO data/backups/<db>-v<from>-<ts>.db` (0600, dir 0700); each step is one transaction; rebuild steps toggle FKs outside the transaction. Only `src/index.js` boot and `scripts/migrate.js --apply` migrate; other scripts call `assertSchemaCurrent()`. Rollback is restore-the-backup only (quickstart §4 of spec 006). Steps: v1–v6 spec 006 (provenance, new tables, scoped rebuild, FTS triggers, backfill, forget content key), v7 spec 007 (`007-llm-usage.js`: `llm_usage` + `prefilter_log`, `CREATE … IF NOT EXISTS`), v8–v9 spec 009 (`008-world-events.js`: append-only `world_events` with no-UPDATE/no-DELETE triggers + `world_snapshots`; `009-life-ops.js`: `life_queue`, `life_claims`), v10 spec 008 (`010-mind.js`: the 13 `mind_*` tables — runs, state, settings, chat activity, digests, nights, episode cursor + log, self-state, self-model, nudges, proactive, exclusions; adds only, never touches 006 tables), v11 spec 010 (`011-arcs.js`: the 8 `story_*` tables — runs, claim reviews, proposals, refusals, journal nights/parts, narrations, state; adds only, never touches `world_events`), v12 spec 012 (`012-chat-influence.js`: `chat_influence_items`, `chat_influence_pending_withdrawals`, `chat_influence_state` — evidence pointers and codes, never message text; adds only), v13 spec 013 (`013-public-site.js`: `public_people`, `public_journal`, `public_state`, `public_votes`; adds only), v14 spec 016 (`014-scenes.js`: `story_scenes` — one row per outing scene version: narration, detail, owner edit, tone + its outcome word, tier, skip code, heavy_window, v1's code fact sheet; adds only), v15 spec 019 (`015-phone.js`: `story_messages` — one row per text turn with a fictional cast member; adds only), v16 plan 020 F2 (`016-thoughts.js`: `story_thoughts`; adds only), v17–v21 plan 020, all adds only (`self_stance*`, `story_dreams`, `story_standing*`, `story_check_*`, `review_*`). Latest = 21.
- **Schedule overrides (spec 014, sched)**: `schedule.override_set` / `schedule.override_cleared` are owner-only and chat-forbidden (`schedule.` prefix; not `director.*`, so a rewind removes them with their consequences). Their consequences are engine events with an owner cause (self by R3): today's re-plan (`plan.made` listing `overrides`) and `decision.expired {reason:'schedule', overrideId, subjectJid?}`. A chat outing kept through a re-plan stays an anchor (`decisionId` + `causeEventId` = its amended plan) so it keeps the chat origin and is skipped when its decision goes. `planEdits.blockCause` is the one cause helper (R29).
- **Life fact provenance (spec 009/010)**: an event's origin comes from its cause chain (`appendEvent` taint): a chat-origin cause makes it chat-origin; an owner cause counts as self for an engine event (owner steering is validated fiction, not chat content); owner-written facts pass every audience like self ones, except one with a real-person `subjectJid` (shown only where that person is). Chat-origin story families (`CHAT_FORBIDDEN_TYPES`, incl. `sick.*`, `money.salary`, `cast.*`, `place.*`) are refused for every actor but the owner. These are accepted 009-rule changes (no 009 producer reaches them).
- **Life audience rule (spec 010)**: `story.attach()` plugs 006's `canUseIn` into `innerState` while the `arcs` skill is on (off → 009's same-chat fallback). A chat-derived life fact is checked at its chat evidence time, never the life event's own time: `innerState`'s origin lookup walks the cause chain to the earliest event with the same origin (a `chat.trigger` / `claim.flagged`), and a decision keeps `originAt[jid]` (earliest event per origin). Chat-origin activities (adopted outings) credit no shared time or contact to the self-origin relationship drift.
- **Fire-and-forget learning**: Heuristics and batch analysis never block the response pipeline
- **Warmup system**: Days 1-3 are reactions-only; text responses gradually increase over ~3 weeks. State stored in `data/warmup.json`
- **Names in text**: `textHasName` (`src/utils/nameMatch.js`): starts at a word boundary; up to 3 letters must also end at one ("sam" isn't in "same"), longer ones may carry an ending.
- **Mentions**: an @-mention counts only when a `mentionedJid` matches the bot's own identities (`sock.user.id`, `sock.user.lid`, `WA_PHONE_NUMBER`; device suffix stripped). Tagging a friend is not a mention; unknown bot identity → not mentioned. Single source: `src/utils/mentions.js` (used by events.js, decisionEngine.js, bill-split). A reply to any of his own messages in that chat — text or media (voice note, sticker, captionless image) — scores as a reply to him (factor 5) in `decide()`, as in the life gate.
- **Image requests**: override a skip only when directed at the bot (DM, @-mention, name/alias, reply to the bot) AND explicit (`isExplicitImageRequest`); only over a probability skip — never rate_limited/burst_cooldown/warmup. The "[SKIP] on an explicit request → generate anyway" fallback follows the same rule, and so does the image-EDIT fast path (a text reply to an image, `isImageEditForBot`): DM or mention factor ≥ 5 only, over a probability skip at most, warmup allowing text.
- **Skill flows**: an active flow (bill-split) is not a reply override in `decide()` — a message the skill claims never reaches it; everything else in that group is scored normally (rate limit, caps, burst) and doesn't keep the flow alive.
- **Sends**: a turn counts as replied (relay confirmed, life catch-up settled, `onReplySent`) only when a send went out — a send helper returning null on a socket error doesn't count; DRY_RUN does. Nothing out → a `send_failed` block outcome. The model's `[REPLY:<id>]` target wins over quoting the trigger (`quoteOptions` in actions.js); with no marker a live reply quotes its trigger only when it isn't answering the chat's latest line — something (his own lines included, reactions not) arrived after the trigger, or the last speaker isn't the trigger's sender (`triggerNeedsQuote`, read at send time); a DM reply to the latest message never quotes.
- **Debounce vs revoke/edit**: at flush the buffered messages are re-read from the DB — a message revoked while buffered is dropped (no turn if none is left), an edited text message carries its new text. Each buffered message keeps its own raw WAMessage: the turn's `context.rawMsg` (the reply's quote, the read-receipt / life-queue key) is the processed message's, never the newest line's, and an edited one's text or caption is replaced with the edited text, so a reply never quotes deleted or edited-away content.
- **Per-chat lock**: live turns (`flushBuffer`), relay dispatch and life's catch-up drain share one lock core (`holdChat` in `events.js`); `withChatLock(chatJid, fn)` hands `fn({ turnSignal })`, a locked job's 90 s budget counts from its own start, starting it aborts an overrun turn of that chat, and messages buffered meanwhile flush after it.
- **Cap catch-up** (`src/behavior/capCatchUp.js`): when `checkHourlyCaps` blocks a group message, `decide()` still scores it (score, roll, or the mention override; no `checkBurst`, which would trip a cooldown — the pass checks the burst side-effect free with `inBurst`) and, only if he'd have sent text, keeps ONE in-memory pending entry per group (last ≤ 3 trigger ids, mentions kept first; any-mention flag = the group-cap exemption; first/last skipped time). The skip reason is unchanged; `factors.catchUpQueued` says whether it queued. A 60 s unref'd timer walks groups oldest first, sequentially (each fire uses a global slot): it fires once `checkHourlyCaps(group, {isMention})`, the rate limiter/burst, warmup (text) and — with life on — availability (`free` or in a phone check, like proactive) allow it; while he isn't available it stays pending (not handed to `life_queue`). Dropped when older than the max age, muted, he has sent anything in the group since the first trigger, or no trigger is prompt-visible any more (re-read under `withChatLock`). The turn is `processMessage(…, {catchUp: {cap: true, triggerIds, itemIds: []}})`: no learning, no life gate, no second roll in `decide()` (caps/rate limit re-checked; `factors.mention`/`question` still computed from the triggers, so a mentioning trigger keeps the mention threshold), never pre-filtered, `>>>` on the triggers, a "you held back for ~N min" prompt note; the model may still `[SKIP]`, and the entry is removed before the turn, so one attempt per group. Groups only; catch-up turns (life's or this one) and proactive openers (which call `checkHourlyCaps` directly) never queue one. Lost on restart, like cooldowns. DRY_RUN is honoured by the send path.
- **Stale turns**: when the 90s in-flight guard fires, the chat lock is released but the slow turn keeps running; it is aborted (`context.turnSignal`) only when a newer turn starts for that chat, and `index.js` checks the signal before each send — no double replies, no half-sent replies.
- **LLM skip signal**: If LLM returns `[SKIP]` or `SKIP`, interpreted as intentional decision not to respond
- **Cooldowns are in-memory**: Burst cooldowns reset on restart
- **One copy, boot check**: `src/utils/instanceLock.js` (`data/.instance-lock`, a dead or foreign holder is stale) and `bootCheck.js` run before migrations. Unlinked with no terminal: exit 78 (service files don't restart on it), or the dashboard stays up with no WhatsApp connection if it's on, so it can link. `scripts/pair.js` prints `PAIRING CODE:`, which the dashboard's pairing job reads.
- **ESM modules**: Project uses `"type": "module"` — all imports are ES module style

## Configuration

All config via `.env` (see `.env.example`). Key variables:

- **LLM roles**: one block per role, generated into `.env.example` from `src/brain/roles.js` (`npm run gen:env`). Mouth keeps the old names (`LLM_PROVIDER`, `LLM_MODEL`, `LLM_EFFORT`, `LLM_MAX_TOKENS`, `LLM_FALLBACK_PROVIDER`, `LLM_FALLBACK_MODEL`, `LLM_TIMEOUT_MS`, `LLM_BUDGET_USD`); clerk `LLM_CLERK_*` (empty → inherits mouth), mind `LLM_MIND_*`, fun `LLM_FUN_*`, gate `QUALITY_GATE_*`, Jev `JEV_MODEL`/`JEV_TIMEOUT_MS`/`JEV_BUDGET_USD`; metered labels `LLM_{SENSES,IMAGE,VOICE,BILL,PROBE}_BUDGET_USD`. `LLM_MONTHLY_BUDGET_USD` is the global cap. `LLM_TEMPERATURE`, `TRANSCRIPTION_MODEL`.
- **Keys**: each provider uses ONLY its own key — `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `OPENROUTER_API_KEY`, `GLM_API_KEY`, `XAI_API_KEY`; `LLM_API_KEY` is the OpenAI key only (a warning fires when it is set with another provider); `LLM_LOCAL_API_KEY` is the optional Bearer for the `local` provider (never falls back to another key). Jev uses `JEV_API_KEY`, else the OpenRouter key.
- **Pre-filter**: `JEV_PREFILTER_ENABLED` (boot default of the `jev-prefilter` skill), `JEV_PREFILTER_MODE` (`shadow`|`enforce`), `JEV_PREFILTER_SKIP_BELOW`
- **WhatsApp**: `WA_PHONE_NUMBER`
- **Behavior**: `RESPONSE_RATE` (base probability, default 0.15), `SLEEP_START_HOUR`/`SLEEP_END_HOUR`, `TIMEZONE`

### Auth

- Basic-auth (user + bcrypt pass hash)
- 30-day signed session cookie (`dash_session` = `<issuedAtSec>.<nonce>`; the server refuses one older than 30 days or without an issue time, so a copied cookie expires too) — frontend POSTs `/api/login` on boot to convert basic-auth into the cookie. The audit actor of every write is `actorOf(req)` (`auth.js`) = `DASHBOARD_USER`
- Stricter rate-limit on `/api/login` (20/min) vs global (300/min); plus a per-TCP-peer basic-auth throttle (20 attempts/min, before bcrypt, no loopback exemption) in `basicAuthValidator`
- `trustProxy` is off: the CIDR gate and limiters key on the socket address, never `X-Forwarded-For`. Behind a local reverse proxy every client would look like the proxy — don't put one in front without revisiting this
- `DASHBOARD_READONLY=true` blocks all write methods. Default is `true` — flip to `false` once you're ready to edit state
- CSRF: when `DASHBOARD_READONLY=false`, every write must carry `X-CSRF-Token` header matching the `csrf_token` cookie issued at login

## Mind (spec 008)

A slow, central "mind" on top of the reply path: it notices, thinks a few times a day, sleeps on the day, keeps a short self-model and may (in shadow, by default) draft openers. Everything lives in `src/mind/`; **the rest of the app imports only the facade `src/mind/index.js`** (`startMind` in `index.js start()`, knob getters in `decisionEngine.js`, prompt surfaces in `systemPrompt.js`, owner writes in `routes/mind.js`). Inert until the `mind` skill is on (`MIND_ENABLED` is only its boot default). Design: `specs/008-mind/{spec,plan,tasks}.md`, `contracts/*`.

- **Cadence** (`cadence.js`) — driven by `life.onTick` (a 15-min fallback timer if no tick in 20 min), one serial job queue. Each pass: the **pulse** (`pulse.js`, code only: cursor scan → `mind_chat_activity` counters, back-off `replied_at`, the "don't text me first" prefilter, expiries, retention, degraded recovery; also while paused) → ≤ 1 **sleep** (one per night; one catch-up sleep after downtime, older nights `missed`) → ≤ 1 **glance** (Jev, `mind.glance`, ~45 min while awake; sees counters labelled C1…Cn, no text/names) → ≤ 1 **think** (`mind` role, `mind.think`; on a glance want, a life anchor or schedule; daily cap + min gap) → dispatch of due queued openers. Awake = `life.isAwakeAt` when life is on, else outside sleep hours. The first pass after the skill turns on seeds every cursor to MAX — history is never analysed in bulk. The first live day (`first_enabled_at`, the review window) starts on the first pass with the skill on and `DRY_RUN` off — every pass retries it, so switching `DRY_RUN` off live is enough.
- **Digests → episodes** — a think reads per-chat clerk digests (`mind.digest`, one clerk call per chat, eligible lines only: no `no_learn`, reactions or disappearing lines, fenced as untrusted). Sleep writes one daily **episode per chat** (`mind.episode`) as a 006 memory (`category:'episode'`, `attribute:'day:<night>'`, origin = that chat, evidence = every line read) and weekly compressions (`mind.weekly`, `week:<…>`, supersede the dailies). Prompts read episodes only through `recallEpisodes(audience)` (006 rule incl. the join-time floor across chats; same chat uses 006's same-chat rule): ≤ 2 under "Recently:" in the per-turn recall head. Revoke/edit nights are rebuilt (≤ 4 per sleep); forgotten nights never.
- **Self-state line** (`selfState.js`) — enum mood/base mood, ≤ 3 `today` picks of digest notes, ≤ 3 intentions; origins written by code, every element re-checked with `canUseIn` and its basis re-read by PK on every render. Rendered in the **per-turn tail** (≤ 160 chars) — never in the cached core; '' while imitating, during a life embargo, when degraded or the skill is off; no mood word while life is on (life's inner-state line owns feelings). Sleep output is staged and handed over at the first glance of the morning.
- **Self-model** (`selfModel.js`) — ≤ 1500 chars in the cached core (`## How you've been lately`), byte-stable until a version is activated. Proposed only by the content-free `mind.selfmodel` call every `MIND_SELF_MODEL_EVERY_NIGHTS` nights (counts and enums in, no chat text or names), then scrubbed in code (shape, provenance — a fell-back run is refused — change budget, forbidden topics, fixation, identifiers, names, 4-gram overlap with digests) and a fail-closed harm gate (`mind.selfmodel.harm`). **Review first**: proposals wait for the owner; the first live enable opens a `MIND_REVIEW_DAYS` (14) review window, after which the default mode `window` auto-applies at sleep unless the owner picks `review` on the Mind page. Owner approve/edit/revert activate at once.
- **Levers + bands** (`levers.js`, `knobs.js`) — the only way a mind run changes behaviour: nudges on five allow-listed knobs (`responseRate`, `groupResponseRate`, `reactTendency`, `replyLength`, `proactiveAppetite`), clamped to owner bands and a max step, with TTL, cooldown and ≤ 6 active; refused when the run fell back or the current value is already outside its band. Owner band edits stay inside `knobs.HARD_LIMITS` (responseRate factors 0.01–2, floor/ceil ≤ 0.5, maxStep (0, 0.1]; multipliers 0.25–2, maxStep (0, 1]), mirrored by the route's own check. They live in `mind_nudges` + an in-memory overlay read by sync getters, re-clamped at read time; never `config`, `.env` or skills. The owner's values win when the skill is off, the mind is paused, a band is disabled, or the owner PATCHes that knob.
- **Proactive** (`proactive.js`) — think `reach_out` → 12 code eligibility checks (exclusions + the opt-out lookback, back-off, caps, A9 basis rule: a basis from chat X supports Y only if X === Y or 006's `canUseIn` with the join-time floor) → intent (`mind.draft`, audience-filtered input) → voice (mouth, `mind.proactive`) + gate (`mind.gate`; must give a score ≥ `MIND_PROACTIVE_MIN_SCORE`). **Shadow** (the default) only stores `shadow`/`would_send` rows for review; **live** needs the Mind page switch AND `OWNER_JIDS`, queues, and `dispatchDue` re-checks everything inside `withChatLock` (fresh audience, content hash, turn signal, `DRY_RUN`) before the one `sendText`. Never to an owner JID. Opt-outs ("don't text me first", DMs and groups, unexpired disappearing lines included) become person exclusions: Jev confirms (`mind.dontText`, ≤ 10/h); a Jev failure, the rate limit or a disappearing line → detected anyway (fail closed). The eligibility lookback (180 days, regex) covers lines the pulse never saw and skips a line Jev already cleared only while its text is the one Jev judged (`mind_settings.dont_text_jev_cleared`: id + sha256 of the text, never the text, ≤ 500; an edited line is re-checked).
- **Deletion hooks** (`hooks.js`, via 006's `onItemsDeleted` / `onPersonPurged` / `onIdentityChange`) — forget fences the night; revoke/edit delete the episode + request a rebuild, cancel the chat's pending drafts (and drafts based on it) and null mind free text — only rows made at or after the message (`msgTs`, less 5 min skew); cause `'owner'` (a dashboard `deleteMemory`) logs a deleted episode as `tombstoned` and does the same with `msgTs` = the deleted memory's `created_at`. A hook failure on forget/revoke/edit never undoes it: logged, audited `mind.hook.fail`, and the mind goes **degraded** (no self-state line, no dispatch) until the pulse recovers (the marker is kept in `mind_settings.degraded`, so a restart doesn't drop the recovery). Purge errors propagate and roll the purge back (also with the skill off).
- **Pause** (Mind page, durable) stops glance/think/sleep/drafts and cancels queued sends; the pulse keeps counting and detecting opt-outs; knob getters return owner values. Prompt surfaces (self-state line, "Recently:", self-model) are not gated on pause — turn the skill off to remove them.
- **Budgets** — the `mind` role (`LLM_MIND_BUDGET_USD`) + 007's global cap, checked by `mindBudgetOk` before every run: think/draft stop at (100 − `MIND_SLEEP_RESERVE_PCT`)% of the mind budget or 70% of the global cap; sleep/self-model at 100% / 90%; an unpriced mind model fails closed. Caller labels are all `mind.*` (`mind.think`, `mind.sleep`, `mind.selfmodel`, `mind.selfmodel.harm`, `mind.draft`, `mind.proactive`, `mind.gate`, `mind.digest`, `mind.episode`, `mind.weekly`, `mind.glance`, `mind.dontText`; `fun.proactive` for the shadow A/B), so `GET /api/mind/status` and the Usage page show per-caller spend. Mind-caused clerk calls have their own daily cap.
- **Mind page** (`#mind`, `pages/mind.js`, polls every 30 s) — status bar (on/paused, proactive mode, review state, spend vs budget, reminders), self-state, runs, digests/episodes, self-model versions with diff/approve/reject/revert/edit, nudges + bands, proactive drafts, exclusions. Writes need `DASHBOARD_READONLY=false` + CSRF, are audited and rate-limited (see Writes).
- **Guards** — `scripts/mind-tests/11-guards.test.js`: only `proactive.js` sends; no SQL on 006 tables from `src/mind` (reads go through `src/memory/mindReads.js` / `recall.js`); no config/.env/skill writers; no persona strings; no chat/model text in logs; the Mind page has no raw HTML sinks. ## Web search & browsing

The bot can look things up mid-conversation. Search uses a **self-hosted SearXNG** JSON API (no API key); browsing uses a **Playwright headless Chromium** (renders JS).

- **Mechanism** — a marker + re-prompt loop inside `generateResponse` (`src/brain/contextBuilder.js`), not provider tool-calling, so `llm.js` and all 6 providers are untouched. The LLM emits `[SEARCH: query]` / `[BROWSE: url]` as its whole message; the tool runs; sanitized, fenced, length-capped results are appended to the user message; the LLM is re-prompted to answer in persona voice. Intermediate results never leave `generateResponse`, so the final text still flows through media-marker extraction + `postProcess` + quality gate unchanged.
- **On/off** — the **`web-search` skill** in the dashboard Skills tab is the runtime master switch. It's a *manifest* skill (`src/skills/web-search.skill.js`): `shouldHandle()` always returns `false`, so it never intercepts messages — it only provides the tab row + toggle. The loop and the system-prompt injection both gate on `isSkillEnabled('web-search')` (`src/skills/skillRunner.js`). `WEB_SEARCH_ENABLED` is only its **boot default** (via `enabledByDefault`); the toggle is in-memory and resets on restart. `WEB_SEARCH_ENABLED=false` is the durable off-switch.
- **Latency budget** — `processMessage` is wrapped in a 90s in-flight guard (`IN_FLIGHT_SAFETY_MS`, `events.js`). `maxHops=1` (default) keeps a web turn within it; `index.js` also credits the generation time against the subsequent `waitResponseDelay`. `maxHops=2` (chain search→browse) requires raising `IN_FLIGHT_SAFETY_MS`.
- **Security** — `browseUrl` URLs come from untrusted group chat, so `webBrowse.js` runs an SSRF guard (rejects non-http(s), private/loopback/link-local/`169.254.169.254`/multicast — also as IPv4 inside an IPv6 literal (`[::ffff:7f00:1]`, NAT64, IPv4-compatible) —, the bot's own dashboard host:port and the SearXNG host; re-checks after redirects). `WEB_BROWSE_ALLOW_PRIVATE=true` disables it — keep it false. The app-layer guard is best-effort; the supported hardening is **network-level egress filtering**. Fetched content is sanitized (`sanitizeWebContent` strips marker-looking tokens + `@digits`) before being fed back, to stop a malicious page from injecting an `[IMAGE:]` marker that would bypass the quality gate and trigger a real image send.
- **Setup** — SearXNG must enable JSON output in its `settings.yml` (`search: { formats: [html, json] }`). Playwright is in `dependencies`; after `npm install` run `npx playwright install chromium` (~300MB). If Chromium is absent, browsing degrades to null and search still works. Web ops run under `DRY_RUN` (they're read-only generation, not a send). Test with `npm run test:search`.
- **Tuning** — `config.webSearch.*` (`src/utils/config.js`); `maxResults`/`maxHops`/`searchMaxPerHour`/`browse.{enabled,maxPerHour,maxConcurrent}` are dashboard-mutable via `PATCH /api/config`. `searxngUrl` and `browse.allowPrivate` are `.env`-only (SSRF surface).

## Voice calls

The bot answers and places cellular calls on a dedicated gateway phone. Asterisk (`deploy/asterisk/`) hands every call on the phone's SIM to the ARI app (`src/calls/ari.js`); `callManager.js` bridges it over RTP (`rtp.js`, resampled) to ONE Gemini Live session (`liveSession.js`; an old `CALL_PROVIDER` line is ignored with a warning). One call at a time (single line), capped at `CALL_MAX_MINUTES` with a wrap-up nudge. Runs in the main process; every callback is guarded so a failure ends the call, never the process.

- **On/off** — the `calls` manifest skill is the kill switch (`CALLS_ENABLED` = boot default): while off, inbound calls are refused busy before answering and the dashboard can't dial.
- **Context + privacy** — `callPrompt.js` builds the prompt from the person's DM audience (a known caller ID maps to that person — accepted risk, caller ID can be spoofed), or a group's when the callee is a fresh member of it (`canUseChatContent`). Call memories belong to the caller's DM (spec 006). After the call one clerk call (`call.summary`) writes the summary memory. Life adds one `callStateNote` line; calls are exempt from life's gate.
- **Dialing** — from the person/group pages only; the number comes from the person's identity and must match `CALL_ALLOWED_NUMBER_RE`. Calls and transcripts are stored in `calls` / `call_transcript`; `CALL_DEBUG_AUDIO=true` saves audio under `data/calls-debug/` (troubleshooting only).
- **Tests** — no offline suite yet; `scripts/call-echo.js` and `scripts/call-loopback-test.js` need a live Asterisk.
